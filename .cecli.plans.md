# Development Plan for CLI-57: Add deep merge support for array fields in .cecli.conf.yml

## 1. Project Overview
- **Problem Statement**: The current configuration merging logic in `cecli` performs shallow merges on array fields for both `.cecli.conf.yml` and `.cecli/conf.yml`. This prevents users from additively extending configuration arrays (e.g., `read`, `rules`, `skills_paths`) without completely overriding default values, making incremental configuration difficult.
- **Project Objectives**: To enhance `cecli`'s configuration management by introducing deep merge behavior for array fields in `.cecli.conf.yml` while maintaining shallow merge for `.cecli/conf.yml`, ensuring backward compatibility, and improving user experience for additive configurations.
- **Scope**:
    - Implement deep merge logic for specified array fields in `.cecli.conf.yml`.
    - Preserve existing shallow merge logic for `.cecli/conf.yml`.
    - Identify and apply deep merge to key array fields: `read`, `rules`, `skills_paths`, `mcp-servers-files`, `subagents_paths`, `tools_paths`, and potentially others as identified.
    - Ensure deduplication of entries during deep merge.
    - Maintain order preservation for existing and new array entries.
    - Develop comprehensive unit and integration tests for both merge behaviors, deduplication, and error handling.
    - Update relevant documentation and provide examples.
- **Exclusions**: Changes to configuration file precedence (command-line arguments > `.cecli.conf.yml` > `.cecli/conf.yml` > default values) are out of scope. Changes to non-array fields' merge behavior are also excluded.
- **Success Criteria**:
    - `.cecli.conf.yml` successfully performs deep merges on array fields, appending unique new entries while preserving order.
    - `.cecli/conf.yml` continues to perform shallow merges on array fields, replacing existing arrays.
    - All identified array fields (e.g., `read`, `rules`, `skills_paths`) correctly support their respective merge behaviors.
    - Existing configurations function without regressions.
    - Comprehensive test suite passes with 100% coverage for new/modified logic.
    - Documentation clearly explains new merge behaviors and provides usage examples.

## 4. Problem Analysis and Goals
- **Problems**:
    - Inability to incrementally extend configuration arrays in `.cecli.conf.yml`.
    - Users must manually replicate default array values when adding custom entries, leading to verbose and error-prone configurations.
    - Lack of a clear distinction in merge behavior between `.cecli.conf.yml` (project-specific, higher precedence) and `.cecli/conf.yml` (user/global defaults).
- **Goals**:
    - Enable seamless, additive configuration for array fields in `.cecli.conf.yml`.
    - Provide a more intuitive and flexible configuration experience for users.
    - Standardize merge behaviors based on configuration file hierarchy and purpose.
    - Improve maintainability of configuration files by reducing redundancy.
- **Why Needed**: This feature significantly enhances the usability and flexibility of `cecli`'s configuration system, addressing a common pain point for users who need to extend default settings without full overrides. It aligns with best practices for layered configuration management.
- **Bottlenecks**: The primary bottleneck is the current monolithic merge logic that treats all array fields uniformly, regardless of their source or intended behavior.

## 5. Architecture Overview
The proposed architecture involves modifying the configuration loading and merging mechanism within `cecli`.

**Current State (Simplified)**:
```mermaid
graph TD
    A[Default Config] --> B{Load Config Files}
    B --> C[Merge Logic (Shallow)]
    C --> D[Final Config]
```

**Proposed State**:
```mermaid
graph TD
    A[Default Config] --> B{Load Config Files}
    B -- .cecli.conf.yml --> C{Detect Config Type}
    B -- .cecli/conf.yml --> C
    C -- .cecli.conf.yml --> D[Deep Merge Logic (Arrays)]
    C -- .cecli/conf.yml --> E[Shallow Merge Logic (Arrays)]
    D --> F[Final Merged Config]
    E --> F
```

**Key Design Patterns and Architectural Decisions**:
- **Strategy Pattern**: Implement different merge strategies (deep vs. shallow) based on the configuration file type.
- **Configuration Layering**: Reinforce the existing hierarchy by applying distinct merge behaviors at different layers.
- **Modular Merge Logic**: Encapsulate the deep merge logic for arrays to be reusable and testable.
- **Backward Compatibility**: Ensure that existing configurations continue to work without modification.

**Components Involved**:
- **Configuration Loader**: Responsible for reading `cecli.conf.yml` and `.cecli/conf.yml`.
- **Merge Resolver**: New component or modified existing logic to determine which merge strategy to apply based on the config file path.
- **Deep Merge Utility**: A new or enhanced utility function specifically for merging array fields deeply (appending unique elements, preserving order).
- **Configuration Fields**: Identification of specific array fields that require deep merge.

**Constraints and Assumptions**:
- **Constraint**: Existing configuration file precedence must be maintained.
- **Constraint**: Backward compatibility for existing configurations is paramount.
- **Assumption**: YAML parsing library supports flexible data structure manipulation required for deep merging.
- **Assumption**: Performance impact of deep merging large arrays will be acceptable.
